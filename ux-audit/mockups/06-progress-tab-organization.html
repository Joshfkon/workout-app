06 · Progress tab — same data, organized around the question "am I progressing?"

The Progress nav item opens a page titled Analytics with five tabs (Body · Goals · Strength · Volume & Trends · Wellness), defaulting to Body. The data underneath is genuinely strong — lift trends, plateau detection, DEXA-anchored composition trends, adaptive volume — but the organization works against it: duplicate charts, a strength ranking filed under Volume, two contradictory volume-target systems, a settings card in the middle of body-comp analysis, and a global time-range control that silently affects only two of the five tabs. Proposal: four tabs with a new Overview as the default, each detail tab owning one topic and its own controls.

Today this tab stacks eleven full-height Recharts cards plus four self-fetching input widgets — roughly 5,000 px of scroll where most cards show "No data for this period". Small multiples put every metric on one screen: value, delta, 30-day shape. Tiles the user has never logged collapse under "show more" instead of rendering as empty charts. The input widgets (hydration tracker, cardio log, recovery card) return to a single compact "Today / Check in" row — logging is one tap away without four input cards leading an analytics tab. Bonus: only the tapped metric's full chart needs to mount, cutting most of the tab's render cost.

Implementation notes. Keep the existing deep-link scheme working: ?tab=body, ?tab=strength&section=lift-trends etc. should map onto the new tabs (strength and volume → training, goals → body#targets / overview) so home tiles and notifications don't break. The reorganization is also the natural moment to split the 3,144-line analytics/page.tsx into per-tab components that fetch on activation — today all five tabs' queries fire on mount regardless of which tab is shown (flagged as P1-2 in the July audit). The Overview tab needs no new data: it composes computeLiftTrends, the adaptive-volume hook, useBodyCompTrend, and the active target — all already fetched by this page.
